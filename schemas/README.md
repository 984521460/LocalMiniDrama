# Versioned JSON Schemas

This directory is the reviewable source of truth for cross-module transport contracts.

- `v1` currently means the exact contract version `1.0.0`.
- Consumers must reject missing, malformed, and unknown versions; forward compatibility is never assumed.
- `result-envelope.schema.json` and `contract-error.schema.json` are a schema set. Register both `$id` values when using a JSON Schema validator.
- Error messages are fixed by error code. Provider response bodies, exception text, credentials, prompts, and other raw upstream data must never be copied into a result envelope.
- Task-specific payload Schemas are added by the phase that owns each task. This base layer intentionally does not guess future narrative payloads.
- `v4/workflow-registry.schema.json` fixes the executable-canvas node types, stable port value types, cardinality, and required-input metadata for registry version `4.0.0`.
- `v4/workflow-execution-plan.schema.json` fixes the canonical graph snapshot, stable enabled/disabled semantics, per-node non-secret configuration, content hash, and topological execution-plan contract. Credential-bearing fields accept only opaque `credential:v1:<UUIDv4>` references.
- `v4/workflow-run.schema.json` fixes the immutable graph binding, workflow/node run states, bounded retry counters, timestamps, safe evidence payloads (including strict opaque credential references), and deterministic node ordinal projection.
- `v5/character-version.schema.json` defines the exact structural Identity, Appearance, Costume, and Voice record shape under one stable Character. Every read and write boundary additionally runs `createCharacterVersionRecord` for cross-field relation validation, including self-parent rejection.
- `v8/voice-profile.schema.json` defines the secret-free public VoiceProfile projection. Internal records bind one immutable Character Voice version to a provider-neutral preset key and an opaque CredentialVault reference; the reference is never returned by the public projection. Runtime and migration `0012` enforce owner, revision, evidence, and active-selection chains.
- `v8/bgm-license.schema.json` and `v8/bgm-track.schema.json` define the local BgmProvider boundary. Every candidate binds a same-drama ready Audio AssetVersion to a self-identifying, explicit user-attestation record and explicit export/modification rights. Persistence assigns each license UID to one immutable track UID and cross-checks the complete track snapshot against the independent license fact. The attestation records the user's claim; it does not independently determine legal validity. User absolute paths and credentials are not representable in the license projection; attribution-bearing licenses are intentionally deferred to a future version with a separately reviewed attribution contract.
- `v8/audio-mix-plan.schema.json` defines a deterministic integer-millisecond and integer-millidecibel mix plan. Runtime derives merged BGM ducking windows from one trusted AudioTimeline, requires an export-eligible same-drama BGM track, bounds foreground/native/BGM gains, fades, attack/release and loop count, and grants execution trust only after replaying an external immutable envelope. The public plan binds source identities and hashes but cannot represent storage paths, URLs or credential references.
- `v8/production-timeline-snapshot.schema.json` defines the sole ordered input for later normalization and FFmpeg assembly. It freezes each video clip, each shot's succeeded GenerationHistory output evidence, every unique dialogue/native audio source, the full subtitle track, deterministic mix plan, export-eligible BGM record and complete portable AssetVersion evidence. Runtime requires same-drama ready ownership, authoritative GenerationHistory lookup, exact run/asset/output-version binding, unique shot/history/media identities, cumulative integer-millisecond continuity, exact cross-plan hashes and an external immutable envelope keyed by the expected snapshot UID; reordering creates a new snapshot and never rewrites an earlier one.
- `v8/media-export-profile.schema.json` fixes the MVP export target to 1920×1080 16:9 MP4, 24 FPS CFR H.264/yuv420p video, 48 kHz stereo AAC audio, ASS subtitle burn-in and faststart muxing. `v8/media-probe-evidence.schema.json` records only bounded, secret-free measurements after the local adapter rechecks a safe project-relative path, actual file SHA-256, duplicate-aware ffprobe output and a full ffmpeg decode. `v8/media-normalization-plan.schema.json` binds that one trusted profile and exactly one current trusted probe per unique ProductionTimelineSnapshot media version, then derives canonical video and audio normalization inputs. Runtime replays an external immutable envelope before granting execution trust; caller-provided hashes alone are never a trust root. P8-08 does not execute concatenation, mixing, subtitle rendering or final MP4 export.
- `v8/media-export-receipt.schema.json` records P8-09's secret-free local export result after the runtime has replayed a trusted ProductionTimelineSnapshot and MediaNormalizationPlan, rehashed every source, normalized and concatenated every shot, rendered a bounded ASS document, mixed dialogue/native/BGM tracks from the trusted AudioMixPlan, installed the candidate without overwriting an existing target, and rerun ffprobe plus a full ffmpeg decode. The receipt fixes 1920×1080/24 FPS/H.264/yuv420p/AAC 48 kHz stereo/faststart output and binds the actual bytes and measurements to the execution plan. Cross-field path/UID, duration/frame and upstream-plan relations that JSON Schema cannot express are mandatory runtime invariants; a Schema-valid object is not an execution-trusted receipt by itself.
- `v8/media-export-run.schema.json` defines P8-10's public, path-safe queued/running/succeeded/failed projection. A run can only be prepared from one succeeded, enabled `export.final` NodeRun in a succeeded frozen workflow; SQLite stores the complete canonical execution plan and receipt in an append-only companion seal, atomically creates one ready `final_video` AssetVersion on success, and freezes/revalidates the complete output evidence on every read. Browser input contains only the opaque NodeRun UID; execution plans, local absolute paths, credentials and raw process errors are never accepted or returned.
- `v5/scene-prop-version.schema.json` defines the exact structural Scene and Prop visual-version record shapes. Every read and write boundary additionally runs `createScenePropVersionRecord`; consumers resolve only owner-matched versions in the `ready` state.
- `v5/character-candidate-request.schema.json` fixes one local Character candidate request to exactly four outputs and binds it to stable Character, Prompt Semantic, profile, and workflow-manifest identities.
- `v5/character-candidate-batch.schema.json` fixes the complete non-secret request snapshot plus four independent single-portrait result records. Runtime validation additionally binds the request hash, deterministic ordinal URIs, and cross-record uniqueness for result, AssetVersion, URI, and content-hash identities before a batch is exposed or persisted.
- `v5/character-reference-package.schema.json` fixes the locked Identity package DTO: canonical front/side/full-body views, neutral/joy/anger/sadness/fear expressions, structured Appearance and default Costume versions, and one concrete AssetVersion per media slot. Runtime and repository validation additionally bind owner, lock event, deterministic URI, immutable media evidence, and append-only package history.
- `v5/shot-continuity-snapshot.schema.json` fixes one approved planned shot to concrete Character reference packages, Identity and Costume versions, one ready Scene version, and every ready Prop version named by the shot facts. `v5/shot-continuity-comparison.schema.json` exposes deterministic version changes only between adjacent shots from the same approved plan. Runtime and repository validation additionally enforce current approval at seal time, same-drama ownership, current Identity lock, exact fact coverage, append-only evidence, and read-time drift detection.
- `v5/prompt-semantic-versioned.schema.json` fixes Provider-neutral Prompt Semantic output to the current approved ShotPlanning result and one immutable continuity snapshot per shot. Public records expose concrete Character package/Identity/Costume, Scene, and Prop version identities without Provider payloads, model metadata, raw responses, or legacy generic asset-version references.
- `v5/generation-history.schema.json` fixes one immutable terminal generation record to a stored Prompt Semantic version, validated workflow manifest, exact model/seed/input/parameter hashes, terminal result or bounded error reference, and complete output/parent AssetVersion evidence snapshots. Runtime, database, repository, and ZIP validation compare storage provider, URI/path, media hash/type/dimensions/duration, lineage, status, and canonical creation time, rejecting secret-shaped payloads, stale approval, linked-record drift, replacement, non-canonical or duplicate-key evidence JSON, and out-of-order selection events. The v2 project-archive manifest carries this evidence closure with the referenced workflow manifest, Prompt Semantic, terminal histories, and append-only version selections.
- `v6/comfy-workflow-manifest.schema.json` defines one validated ComfyUI API-format workflow manifest and rejects exact duplicate dependency requirements. Runtime creation additionally binds the exact workflow-byte SHA-256, the complete node-type set, model file inputs, application-owned input/output markers, unique input target pairs, unique output markers, and compiler bindings. Formal records are append-only in SQLite, repository reads reject non-canonical or malformed persisted JSON, and dependency checks consume only runtime-branded manifests before reporting missing nodes or model files.
- `v6/remote-task.schema.json` fixes the persisted task state, optimistic version, prompt identity, phase error and recovery contract. A production prepare request may supply its canonical `taskUid` so the immutable `remoteRelativeDir` can be fixed as `jobs/<taskUid>` before any remote side effect; retries reuse the same task identity and idempotency key.
- `v6/remote-execution-request.schema.json` fixes the public production-coordinator request to one workflow byte snapshot, bounded application-owned values, checked upload paths and hashes, and one typed logical output bound to an existing Asset. Production execution accepts only enabled `shot.image`/`shot.video` nodes whose frozen graph snapshot binds the exact Asset, Manifest, remote connection, opaque credential reference, and a SHA-256 of the connection state/version, endpoint, host fingerprint, Comfy endpoint, and remote work directory. The same digest is immutable in `v6/remote-task.schema.json`, contributes to the task request hash, and is rechecked against the actual opened connection before every SFTP, dependency, submission, polling, and download action. Runtime validation additionally rejects hostile descriptors, sparse arrays, non-canonical Base64, traversal, oversized nested payloads, workflow/Manifest hash drift, task/run/node ownership drift, connection evidence drift, and non-isolated job directories before remote side effects.
- `v7/h3-profile.schema.json` fixes revision 2 of the locally measured MiniMax H3 four-step profile: verified model digests, frame grid, canvas, sampler and per-mode real-validation status. The Video VAE digest was independently recomputed from the downloaded official file and is now a verified 64-character SHA-256. T2V, one-image FL2VA, first-and-last FL2VA, and four-image-plus-audio Ref2VA carry measured RTX 4090 evidence; RTX PRO 6000 Blackwell remains unverified.
- `v7/h3-shot-prompt.schema.json` fixes a Provider-neutral prompt compiled from one version-bound Prompt Semantic shot without model parameters, paths, credentials or concrete asset identities in the prompt text. `v7/h3-generation-spec.schema.json` binds that prompt to deterministic 24 FPS / 17k+5 timing, a bounded canvas and exact same-drama reference-media identities. Runtime validation additionally enforces cross-field mode roles, reference order and uniqueness, prompt hashes, canvas area and hostile-input rejection. The local FL2VA and Ref2VA compiler pins the exact upstream workflow-template commit and hashes and binds each safe Comfy input filename back to its AssetVersion/hash evidence. Only the three exact RTX 4090-validated variants are trusted by the Phase 7 evidence gate; other Ref2VA image-count/audio combinations remain `implementation-candidate-unverified`, and production compilation remains separately bounded until Phase 8 integration.
- `v7/h3-video-evidence.schema.json` records output hash and byte count only after an MP4 probe confirms the expected dimensions, 24 FPS frame count and bounded duration, H.264 video, one AAC audio stream, and basic black/frozen-frame thresholds. Runtime validation binds the evidence to the complete normalized generation-spec hash before any version-selection operation.
- `v7/h3-real-validation-matrix.schema.json` separates measured GPU evidence from planned coverage. It records the existing RTX 4090 T2V smoke and 15-second cases plus the Phase 7 four-mode 1.625-second evidence set. Every RTX PRO 6000 Blackwell case remains explicitly unverified.
- `v7/h3-real-gpu-environment.schema.json` fixes the reviewed RTX 4090/runtime projection and all seven FL2VA/Ref2VA model files without an endpoint, credential or private path. `v7/h3-real-validation-receipt.schema.json` binds each locally collected receipt to Profile revision 2, the canonical Profile hash, the exact environment hash, a complete Comfy Manifest, normalized generation input, prompt ID, output AssetVersion and probed video evidence. Runtime rechecks every hash and only counts an exact locally trusted workflow identity. `v7/h3-phase7-evidence-gate.schema.json` reports whether all four RTX 4090 modes have independent receipts bound to the same current Profile and environment; this mechanical completeness signal does not prove GPU provenance or replace human visual acceptance.
- `v7/h3-real-validation-plan.schema.json` fixes the pre-execution RTX 4090 plan to exactly four ordered cases: trusted T2V, first-frame FL2VA, first-and-last-frame FL2VA, and four-image Ref2VA with reference audio. Each case binds the normalized specification, exact Manifest, media evidence filenames, compiled Comfy prompt, output node and expected media shape. `prepared-unverified` remains a pre-run plan status; the exact four reviewed workflows are promoted only by the separate receipt gate, not by plan creation.
- `v7/h3-api-task.schema.json` fixes the public, secret-free MiniMax H3 API task projection. The production API adapter derives requests from the shared generation specification, requires a canonical `Idempotency-Key` operation UUID, durably reserves the request before any chargeable POST, resolves credentials only inside the transport boundary, accepts only the official CN/global HTTPS origins, revalidates referenced AssetVersion evidence before submission, and never places API keys or configured endpoints in workflow, history, logs, or public DTOs. Indeterminate submissions are retained as non-retryable local records until a later reconciliation workflow is explicitly implemented.
- `v9/mvp-benchmark-readiness.schema.json` exposes the fixed Phase 9 production-readiness capabilities and the complete Section 19 acceptance checklist without claiming completion. Runtime assessment derives machine-ready capabilities from the current migrated database and production composition root, keeps Windows release and human audiovisual review explicitly pending, and revalidates the complete DTO against the current runtime/database state before it is returned.
- `v9/h3-local-execution-result.schema.json` is the minimal secret-free receipt returned by the production H3 local execution entry after it re-reads and binds the completed remote task, succeeded generation run, H3 history, workflow node, and ready AssetVersion. The request body reuses `v6/remote-execution-request.schema.json`; the path task UID must already own a validated official H3 execution intent.
- `v9/audio-mode-intent.schema.json` is the secret-free public projection of one locally prepared independent-TTS intent. The persisted internal request and opaque credential reference are never returned. Runtime and SQLite bind the enabled `audio.tts` NodeRun to the current approved Shot and direct Script upstream, exact continuity Character facts, the current active VoiceProfile, and a canonical `v8/audio-mode-plan` hash on every write and read. Preparation performs no Vault read, Provider request, audio write, AssetVersion creation, or readiness transition.
- `v9/mvp-benchmark-session.schema.json` is the immutable, secret-free execution anchor for one Phase 9 benchmark workflow. It binds one drama and frozen graph to all 4–6 official prepared H3 tasks and every prepared TTS intent in topological node order. The plan proves only that the exact external operations are ready to be attempted; it is not a generation receipt, human audiovisual approval, or MVP completion evidence.
- `v9/mvp-benchmark-external-authorization.schema.json` is the immutable, secret-free operator authorization requirement for one frozen benchmark session. It fixes the ready connection evidence, CNY-fen cost ceiling, one-attempt limit, 24-hour maximum window, session-only data scope, required RTX 4090 environment, and return-after-terminal-or-expiry policy. It explicitly requires a separate live environment check and is not execution, billing, media, or human-review evidence. D3B0 keeps session-reserved H3/TTS items blocked at existing production execution entries; consuming this requirement needs a later reviewed live-environment and atomic budget/attempt gate.
